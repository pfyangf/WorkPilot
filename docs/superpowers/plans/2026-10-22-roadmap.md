# WorkPilot 开发路线图

- 日期：2026-10-22
- 依据：`docs/adr/0001-shared-rust-core.md`、`docs/PRD.md`、`docs/TECHNICAL_DESIGN.md`
- 当前可执行计划：`2026-10-22-phase0-rust-workspace.md`

每一阶段都要能单独构建和测试。上一阶段的测试通过并记录兼容性之后，再编写下一阶段的实施计划。本文只排顺序和完成标准，不包含 Phase 1 及之后的代码步骤。

已确认的决定：

- 共享 Rust 业务核心，各端原生 UI。
- 标识使用 UUID v7 字符串。
- 用户编辑过的日报被重新生成时返回冲突，不覆盖原文。
- 同步留在 Phase 4。手机不访问 Windows 本地 SQLite。桌面服务不默认暴露到公网。
- JNI、NAPI、Tauri、SQLite 不进入 Phase 0。

## Phase 0：共享核心

计划文件：`2026-10-22-phase0-rust-workspace.md`。

完成标准：

- `cargo test --workspace` 实际退出码为 0。
- 覆盖任务状态流转、未完成子任务确认、日志追加、已编辑日报保护、DTO 字段。
- `docs/compatibility/phase0.md` 只记录实际命令输出。
- 仓库里没有 Android、HarmonyOS、Tauri 和同步服务工程。

## Phase 1：Windows MVP

完成 Phase 0 后另写实施计划。建议按这些垂直切片拆分，每一片都要有测试：

1. SQLite 迁移和任务持久化。
2. 工作日志持久化。日志追加不改任务状态。
3. 日报版本、来源记录和 Markdown 导出。已编辑正文不能被覆盖。
4. LLM Provider trait、假 Provider，以及一个 OpenAI-compatible 实现。密钥进系统凭据存储。
5. Tauri 2 与 React：任务、日志、日报、设置和空状态。
6. 托盘、关闭到托盘、退出和本地滚动日志。

完成标准见 PRD「Windows MVP」验收清单。桌面整理和 Coding 采集保持不可用。

## Phase 2：Android

先做一次 JNI 验证切片：`arm64-v8a` 的 Rust cdylib 被 Kotlin 加载，并返回一条固定 DTO JSON。验证失败时把错误写入兼容性记录，不把桥接写成已完成。

验证通过后的产品切片：任务查看和新增、基础修改、工作日志、日报查看和轻量编辑、未连接的同步状态。

## Phase 3：HarmonyOS

先在目标 HarmonyOS SDK、DevEco Studio 和真机上验证 NAPI 的构建、链接、调用和打包。失败时鸿蒙端只保留 HTTPS 客户端边界，等待 Phase 4，不阻塞已完成的 Windows 和 Android。

验证通过后的产品范围与 Android 配套端相同。

## Phase 4：同步

另写实施计划。范围：认证、设备授权和撤销、增量同步、幂等提交、失败重试、冲突检测、同步状态显示。

同步载荷排除 AI 密钥、访问令牌、原始 Coding 会话、完整文件路径和本地文件内容。已编辑日报不能被静默覆盖。

## Windows 后续

MVP 之后单独计划，不插入 Phase 0：

- 桌面扫描、规则、预览、移动、操作历史和撤销。测试只用临时目录。
- Coding 工具适配器。先支持手动导入。未接入的工具不显示实时状态。
